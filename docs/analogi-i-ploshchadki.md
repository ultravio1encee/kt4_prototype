# Как проверить ZIP-копию перед восстановлением

**Аналоги и площадки для КТ4** · Команда 25 · Гулиев Ацамаз Тамерланович · 23 ноября 2026 г.

Системный администратор небольшой компании получил ZIP с резервной копией. Архив открывается, но все ли вчерашние файлы на месте и совпадает ли их содержимое с исправной копией? Для нашего прототипа у администратора есть отдельный эталонный JSON. Его заранее составили по исправной копии и сохранили в доверенном месте. Для каждого файла в нём записаны относительный путь внутри ZIP, размер в байтах и SHA-256.

Администратор выбирает ZIP и контрольный JSON в локальном веб-интерфейсе Streamlit. Python-приложение сравнивает файлы и выводит результат по каждому пути. По кнопке «Скачать отчёт CSV» можно получить таблицу в файле `otchet_proverki.csv`. Сверка отвечает на вопрос о составе и содержимом файлов. Возможность восстановить из них работающую систему проверяют отдельно. [Инструкция команды](../README.md) · [Формирование отчёта](../app.py)

## Пять способов проверить копию

| Инструмент | Для кого и для какой задачи | Входные данные и запуск | Что именно проверяет | Ограничение для нашего сценария | Стоимость и свидетельство применения |
| --- | --- | --- | --- | --- | --- |
| **7-Zip** | Администратор или получатель архива проверяет, можно ли прочитать упакованные файлы. | Достаточно ZIP и установленного 7-Zip. В интерфейсе выбрать «Тестировать» или выполнить `7z t backup.zip`. | Читает записи архива и проверяет их внутренние контрольные суммы. В обычном ZIP это CRC-32. | После пересборки у ZIP будут корректные суммы для нового содержимого. Отсутствие ожидаемого файла можно заметить только при сравнении с внешним перечнем. | Бесплатен, в том числе для организаций. Входит в Debian как отдельный пакет. [7-Zip](https://www.7-zip.org/) · [команда t](https://web.mit.edu/outland/arch/i386_deb40/build/p7zip_4.44/DOCS/MANUAL/commands/test.htm) · [пакет Debian](https://packages.debian.org/trixie/7zip) |
| **GNU sha256sum** | Администратор проверяет полученные файлы по опубликованным или заранее сохранённым хешам. | Распаковать копию. Из каталога файлов выполнить `sha256sum --check SHA256SUMS`, указав путь к доверенному текстовому списку. | Для каждого пути из списка читает файл и пересчитывает SHA-256. Сообщает о несовпадении суммы и об отсутствующем файле. | Проверка перебирает только перечисленные пути. Добавленный в каталог файл останется незамеченным. | Бесплатен в составе GNU Coreutils. Ubuntu публикует подписанный список SHA-256 для проверки скачанных образов. [Руководство sha256sum](https://manpages.debian.org/trixie/coreutils/sha256sum.1.en.html) · [процедура Ubuntu](https://documentation.ubuntu.com/security/software-integrity/image-verification/) |
| **BagIt / bagit-python** | Архивист или получатель коллекции выясняет, дошёл ли весь переданный комплект без изменений. | Каталог BagIt содержит файлы в `data/`, описание формата и манифесты. Для манифеста SHA-256 используется `manifest-sha256.txt`. Полная проверка в Python CLI — `bagit.py --validate mybag`. | Сверяет перечень путей с содержимым `data/` и пересчитывает хеши. Выявляет отсутствующий, изменённый и лишний файл. | Обычный ZIP с отдельным JSON нужно преобразовать в структуру BagIt. Достоверность результата зависит от того, откуда получен манифест. | Стандарт открыт, реализация бесплатна. Библиотека Конгресса США описывает использование формата для приёма цифровых коллекций. [RFC 8493](https://www.rfc-editor.org/rfc/rfc8493.html) · [утилита](https://github.com/LibraryOfCongress/bagit-python) · [опыт библиотеки](https://blogs.loc.gov/thesignal/2019/04/bagit-at-the-library-of-congress/) |
| **restic** | Администратор, который уже делает резервные копии в restic, проверяет состояние хранилища. | Нужны репозиторий restic, пароль и доступ к месту хранения. Пример локального запуска — `restic -r /srv/restic-repo check --read-data`. | Проверяет структуру репозитория. Флаг `--read-data` добавляет чтение и проверку всех файлов с упакованными данными. | Требуется хранилище формата restic. Если при создании снимка забыли включить каталог, сам снимок может остаться внутренне согласованным. | Программа бесплатна. Для удалённого репозитория возможны расходы на хранение и чтение. Velero документирует использование restic для резервного копирования томов Kubernetes в версии 1.14. [Команда check](https://restic.readthedocs.io/en/stable/045_working_with_repos.html#checking-integrity-and-consistency) · [проект](https://github.com/restic/restic) · [интеграция Velero](https://velero.io/docs/v1.14/file-system-backup/#how-velero-integrates-with-restic) |
| **rclone check** | Администратор сверяет содержимое двух каталогов, например локального оригинала и копии в облаке. | Нужны доступ к обеим сторонам и клиент rclone. Пример для каталогов — `rclone check etalon kopiya --download --combined report.txt`. | Сопоставляет пути с обеих сторон. Режим `--download` читает содержимое для сравнения. В сводке различает совпадение, различие, путь только в источнике, путь только в копии и ошибку чтения. | В показанном режиме нужен доступ к самим исходным данным. Полное чтение удалённой копии требует времени и трафика. Для нашего случая с одним ZIP и эталонным JSON нужна подготовка входных данных. | Клиент бесплатен, облачный провайдер может тарифицировать обращения. Йельский центр исследовательских вычислений описывает применение rclone для передачи данных между кластером и облаком. [Команда check](https://rclone.org/commands/rclone_check/) · [лицензия](https://rclone.org/licence/) · [руководство Йеля](https://docs.ycrc.yale.edu/data/transfer/) |

## Проверка на четырёх учебных копиях

Исходный ZIP содержал два файла — `alpha.txt` с текстом `hello` и `beta.txt` с текстом `world`. В конце каждого файла был один байт перевода строки. Для каждой строки таблицы ZIP собирали заново. Эталонные пути и SHA-256 во всех случаях оставались одинаковыми. 7-Zip проверял сам архив. Для двух других инструментов файлы распаковывали. Для BagIt их помещали в `data/` и добавляли манифест с исходными хешами.

| Содержимое ZIP | 7-Zip 24.08 · `7z t` | GNU sha256sum 8.32 · `--check` | bagit-python 1.9.0 · `--validate` |
| --- | --- | --- | --- |
| Оба исходных файла | Проверка прошла | Оба файла совпали | Пакет прошёл проверку |
| Удалён `beta.txt` | Проверка прошла | Сообщил об отсутствии `beta.txt` | Назвал отсутствующий `beta.txt` |
| В `alpha.txt` заменили `hello` на `HELLO`, размер остался 6 байт | Проверка прошла | Обнаружил несовпадение SHA-256 у `alpha.txt` | Указал `alpha.txt` и обе разные суммы |
| Добавлен `gamma.txt` | Проверка прошла | Оба файла из списка совпали | Нашёл `gamma.txt` вне манифеста |

Это результаты 12 запусков трёх утилит. Описание restic и rclone в первой таблице основано на документации.

**Ближайший аналог — BagIt.** В опыте он различил все три расхождения и назвал затронутый файл. Та же логика нужна администратору перед восстановлением. Разница видна в подготовке данных. Получателю BagIt нужен оформленный пакет. В нашем сценарии у администратора уже есть обычный ZIP и отдельно сохранённый JSON. Он выбирает их в браузере, получает четыре статуса по путям и сохраняет результат. Совпадение имеет смысл, пока администратор доверяет эталону. Если создать JSON из уже неполной копии, отсутствующий файл в него не попадёт.

Критерий успеха — участник без подсказки называет проблемный путь и объясняет статус по отчёту. Это можно проверить внутри команды до решения о публичной публикации.

## Три вывода для README и защиты

1. **Начать показ с архива, который успешно открывается.** В комплекте команды `backup_missing.zip` проходит проверку `7z t`. Открыть его в приложении с эталоном `control.json` и попросить зрителя найти строку `docs/report.txt` со статусом «Отсутствует». Этот файл был в исходной копии. [Архив с пропуском](../outputs/backup_missing.zip) · [Контрольный JSON](../outputs/control.json)
2. **Показать изменение при том же размере.** В `backup_changed.zip` у файла `docs/report.txt` по-прежнему 5 байт. В таблице рядом со статусом «Изменён» видны два разных SHA-256. Показать эту строку и затем сравнить с исходным архивом, где у обоих файлов статус «Совпадает». [Изменённая копия](../outputs/backup_changed.zip) · [Исходная копия](../outputs/backup_2026.zip)
3. **Дать зрителю повторить проверку и забрать результат.** Предложить ему открыть `backup_extra.zip` с тем же эталоном и скачать CSV. Критерий прост — другой участник может по отчёту самостоятельно назвать путь `notes/extra.txt` и его статус «Лишний». [Архив с дополнительным файлом](../outputs/backup_extra.zip)
